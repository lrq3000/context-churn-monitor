# Automatic Context Monitor backend connection

## Approved intent

The installed GUI repeatedly says `Pair this project with its backend descriptor first` although the current worktree's backend is healthy. Read-only reproduction confirmed the exact descriptor exists and authenticated health returns 200, but `Bridge.request` rejects because only three older worktrees have saved manual pairings. The user approved automatic connection for every project/worktree, compatible release 0.3.1, installed backup/refresh, one independent final review, and squash integration/publication of main plus the original fix branch. The user subsequently cancelled resource-redesign brainstorming: retain the existing per-initialized-location backend lifecycle. A descriptor is a JSON file, not a separate OS process or a per-thread backend.

## Design and alternatives

Use the existing user-wide `alerts.sqlite` connection for an indexed descriptor-path registry, without another database connection, listener, process or broker. A focused `BackendRegistry` owns this metadata; `AlertHistory` exposes it using its existing connection. Backend startup publishes its exact descriptor path after binding/writing it, including custom data roots. Store project identities with the same Windows case/separator normalization as manual pairing. The GUI service resolves only the exact active project and reuses existing bounded descriptor validation, authenticated health and instance/directory checks. Never scan ports, search project trees, guess credentials or forward to another project's listener.

Automatic resolution reads at most nine indexed candidates, rejects more than eight, and performs at most eight health checks concurrently with the existing 2500ms health deadline. Zero healthy exact-project backends produces an actionable unavailable/start-backend error; two or more healthy candidates require an explicit manual selection. Never silently choose the first candidate. Existing explicit manual pairings are authoritative and retain their path/legacy behavior; an invalid explicit selection must not silently fall back. Automatic connection does not rewrite `gui-pairings.json`. Every request revalidates the current descriptor, and uncertain POSTs are never replayed. Registry publication failure must not leak a newly bound listener.

Independent-review correction: resolve a configured relative descriptor path using the same process cwd semantics as prior publication. Before replacement, protect an existing authenticated live descriptor owner with one bounded fresh-socket health probe; malformed/uncertain ownership fails closed. Registered publishers sharing the global store serialize only the synchronous compare/write/register critical section, not network IO. If the file changed since the preflight snapshot, reject publication rather than overwrite it. A handled registration failure restores the prior owned descriptor bytes and rolls back metadata; a same-path duplicate cannot displace a healthy publisher. Distinct-path live backends still require manual selection. This is publication safety, not a backend lifecycle redesign or an assertion of exhaustive filesystem/power-loss atomicity.

Authenticated health checks inherit the existing protocol: a reused loopback listener can receive a retired bearer/instance header before identity mismatch is established. The guarantee is no forwarded action/POST after a mismatch, not zero retired-credential transmission or proof of reading/compromise. A new mutual-authentication protocol is outside this correction.

A one-off manual pairing is insufficient because every new worktree repeats the setup problem. Unbounded descriptor/port scans weaken the current trust boundary and add work. A shared-broker redesign would be a separate architecture task and is explicitly excluded. The registry records only directory/path metadata, not extra bearer secrets; credentials remain in existing descriptor files and the approved local service.
